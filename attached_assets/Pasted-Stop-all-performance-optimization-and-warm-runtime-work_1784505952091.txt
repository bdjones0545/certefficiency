CertEfficiency is still not functional in production:

* New Chat fails.

## Objective

The following production flow must pass from the browser:

```text
Click New Chat
→ local conversation created
→ conversation opens
→ composer enabled
→ user sends message
→ local user message saved
→ Sarah job created
→ Sarah receives request
→ Sarah response normalized
→ assistant message persisted
→ UI refetches
→ assistant message appears
```

A command-line test against Sarah alone is not sufficient. The test must begin in the actual CertEfficiency frontend.

## 3. Fix New Chat first

Inspect the deployed implementation of:

```text
POST /api/conversations
```

This route must not wait for Sarah.

Required backend order:

1. Authenticate the user.
2. Validate the local request.
3. Insert the local conversation.
4. Commit the local database transaction.
5. Return `201` with the local conversation.
6. Start Sarah initialization asynchronously.

Required response shape:

```json
{
  "conversation": {
    "id": "conversation-id",
    "title": "New conversation",
    "status": "active",
    "createdAt": "2026-07-19T00:00:00.000Z"
  }
}
```

Sarah initialization must never turn a successful local insert into a failed HTTP response.

If Sarah returns `400`, `401`, `500`, times out, or returns an unexpected schema:

* preserve the local conversation
* return the local conversation to the frontend
* record initialization as failed
* allow the user to enter the chat
* retry initialization on the first message

Do not put the database insert and Sarah call in the same transaction.

```ts
type CanonicalSarahResult = {

  actions: Array<Record<string, unknown>>;

  jobCompleted: boolean;
};
```

Do not allow frontend or database code to depend directly on Sarah’s native response envelope.
