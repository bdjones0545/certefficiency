Perform a complete production-readiness audit of CertEfficiency’s connection to Hermes and the Sarah certification agent.

## Objective

Determine whether the full Replit → Hermes → Sarah workflow is genuinely production-ready.

This audit must evaluate the entire integration, not only whether individual endpoints return successful responses.

The production path is:

```text
CertEfficiency frontend
→ CertEfficiency Replit backend
→ Cloudflare Tunnel
→ Hermes runtime on the VM
→ Sarah agent profile
→ Sarah’s skills, tools, memory, and knowledge
→ structured response
→ Replit backend
→ CertEfficiency frontend
```

The audit must verify:

* identity
* authentication
* authorization
* request signing
* routing
* conversation lifecycle
* message delivery
* retries
* idempotency
* timeouts
* persistence
* observability
* failure recovery
* security
* deployment configuration
* user experience
* production operations

Do not assume that passing unit tests or receiving one successful response proves production readiness.

---

# Known context

Sarah is the CertEfficiency certification tutor.

The existing system may include:

* Hermes running on an external VM
* Cloudflare Tunnel between Replit and the VM
* signed requests using HMAC and/or bearer authentication
* Sarah-specific API routes
* conversation creation
* message sending
* persistent conversation history
* image or document upload capabilities
* readiness and mastery tracking
* certification-specific knowledge
* structured response contracts
* retries and correlation IDs

Previous failures included:

* new conversations failing to initialize
* messages failing to send
* frontend state clearing before a successful response
* mismatched response shapes
* conversation invalidation issues
* potential similarities between Sarah and Stan integration failures

Treat these as areas requiring explicit regression testing.

# Phase 3: Identity and routing

Verify that requests intended for Sarah cannot be routed to another Hermes agent.

The Replit backend must explicitly resolve:

* agent identity: Sarah
* agent profile
* certification context
* organization or user context
* conversation context
* permissions
* applicable knowledge sources
* applicable skills
* tool access

Confirm that Sarah’s identity is not determined only by frontend input.

The client must not be able to replace:

* agent name
* agent profile
* Hermes profile path
* system prompt
* knowledge vault
* tool permissions
* callback destination
* runtime target

These must be resolved server-side from trusted configuration.

Test that attempts to route requests to Stan, Kevin, Benji, or another profile through Sarah’s API are rejected or ignored.

# Phase 4: Authentication and request signing

Audit the full authentication path between Replit and Hermes.

Verify:

* HTTPS is required
* Cloudflare Tunnel is not bypassed
* secrets remain server-only
* HMAC or bearer credentials are not exposed to the browser
* signatures are generated over a canonical payload
* timestamps are included
* replay windows are enforced
* nonce or idempotency protections exist where appropriate
* signature comparison is timing-safe
* malformed signatures are rejected
* expired signatures are rejected
* missing authentication is rejected
* logs never contain secrets
* secret rotation is possible without a full rewrite

If both HMAC and bearer authentication exist, document why both are needed and which is authoritative.

Do not silently fall back to insecure authentication in production.

Audit any setting equivalent to:

```text
ALLOW_INSECURE
SKIP_SIGNATURE_CHECK
DEV_HMAC
DISABLE_AUTH
```

Production must fail closed.

# Phase 6: Conversation lifecycle audit

Audit the complete conversation lifecycle.

## Conversation creation

Verify:

* a conversation receives one canonical ID
* the ID is persisted before dependent messages are sent
* duplicate clicks do not create duplicate conversations
* create requests support idempotency
* frontend and backend agree on the response shape
* wrapped and unwrapped response formats are normalized
* failures do not leave unusable empty conversations
* failures do not incorrectly clear user input

## First-message creation

If a conversation can be created when the first message is sent:

* creation and first-message delivery must be coordinated
* the frontend must not depend on a race between separate calls
* retries must not create duplicate conversations or duplicate messages
* conversation lists must refresh after success
* failed sends must preserve the user’s text

## New conversation

Verify that pressing “New Chat”:

* creates or initializes the correct state
* clears only the active local draft when appropriate
* does not reuse the previous conversation ID
* updates navigation
* does not lose unsent text without warning
* works after a previous request failed

## Resume conversation

Verify:

* persisted messages load in the correct order
* roles are preserved
* attachments remain associated
* Sarah receives enough history or a server-side summary
* history length limits are handled safely
* stale frontend state does not overwrite newer server state

# Phase 7: Message delivery and response handling

Audit message sending from click to final render.

Verify:

1. User submits a message
2. UI creates an explicit sending state
3. Replit authenticates the user
4. Replit verifies conversation ownership
5. Replit generates a correlation ID
6. Replit writes or reserves the user message
7. Replit dispatches to Hermes
8. Hermes acknowledges the request
9. Sarah processes the request
10. A response is returned or delivered asynchronously
11. Replit validates the response
12. Replit persists the assistant message
13. The UI reconciles server state
14. Loading indicators end
15. Errors remain retryable

The composer must not permanently clear the user’s message before the server accepts responsibility for it.

If optimistic UI is used:

* retain a recoverable copy
* mark pending messages clearly
* reconcile by stable message ID
* prevent duplicate rendering
* support retry

Validate Sarah responses with a schema rather than trusting arbitrary JSON.

Reject or safely handle:

* empty responses
* malformed responses
* HTML where structured text is expected
* unexpected agent identity
* missing conversation IDs
* missing message IDs
* oversized responses
* duplicate callbacks
* stale callbacks

# Phase 8: Synchronous versus asynchronous execution

Determine whether Sarah responses are:

* synchronous
* asynchronous through callbacks
* job-based
* polling-based
* a hybrid

Document the actual model.

If synchronous:

* set explicit connect and response timeouts
* do not leave requests hanging indefinitely
* distinguish timeout from rejection
* ensure proxies and Replit request limits are respected

If asynchronous:

* persist a job before dispatch
* return a stable job or message ID
* validate callbacks
* enforce callback idempotency
* handle out-of-order callbacks
* handle duplicate callbacks
* handle callbacks after user logout
* expose a recoverable pending state
* provide polling or push updates
* expire abandoned jobs safely

Do not maintain ambiguous half-synchronous behavior where the frontend cannot determine whether Sarah accepted the request.

# Phase 9: Timeout, retry, and idempotency policy

Define production policies for every network boundary.

Audit:

```text
Browser → Replit
Replit → Cloudflare Tunnel
Cloudflare Tunnel → Hermes
Hermes → Sarah
Hermes callback → Replit
Replit → database
```

For each boundary, define:

* timeout
* retry count
* retryable errors
* non-retryable errors
* exponential backoff
* jitter
* idempotency key
* maximum elapsed time

Retries must not duplicate:

* conversations
* user messages
* Sarah responses
* mastery updates
* usage records
* billing-related actions
* attachments

Use stable idempotency keys based on trusted identifiers.

Do not retry authentication failures, schema failures, or permission failures as transient errors.
