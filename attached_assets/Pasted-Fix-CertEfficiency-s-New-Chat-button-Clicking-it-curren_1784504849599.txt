Fix CertEfficiency’s **New Chat** button. Clicking it currently does not create or open a new conversation.

## Required architecture

The New Chat flow must be:

```text
Click New Chat
→ create local conversation in CertEfficiency
→ return local conversation immediately
→ update frontend state
→ navigate to the new conversation
→ initialize Sarah asynchronously
→ render Sarah’s opening message when ready
```

The frontend must not wait for Sarah’s `/v1/conversations` response before opening the chat.

## Diagnose the current failure

Trace the complete flow and report where it stops:

```text
new_chat_clicked
frontend_create_mutation_started
conversation_route_entered
conversation_validated
conversation_saved
conversation_response_sent
frontend_create_mutation_succeeded
conversation_state_updated
navigation_started
sarah_initialization_started
sarah_initialization_completed
```

Capture safely:

* whether the click handler fires
* whether `createConv.mutateAsync()` is called
* the exact frontend request URL
* the HTTP status and safe response body
* whether a local database row is inserted
* whether the route returns a conversation ID
* whether the frontend updates `activeConversationId`
* whether navigation occurs
* whether Sarah initialization blocks the response
* whether `createConv.isPending` becomes permanently stuck
* any uncaught frontend or backend error

Do not log secrets.

## Backend fix

Inspect:

```text
POST /api/conversations
```

This endpoint must:

1. Authenticate the user.
2. Validate the request.
3. Insert the local conversation.
4. Commit the database transaction.
5. Return `201` immediately with the canonical local conversation.

Example response:

```json
{
  "conversation": {
    "id": "local-conversation-id",
    "title": "New conversation",
    "status": "active",
    "createdAt": "..."
  }
}
```

Do not await Sarah before returning.

After the response is committed, initialize Sarah asynchronously:

```text
local conversation saved
→ HTTP response sent
→ background Sarah initialization starts
```

Sarah initialization failure must not:

* delete the local conversation
* roll back the insert
* change the successful response into a `500`
* prevent navigation
* disable the composer permanently

Store Sarah initialization state separately:

```text
pending
processing
completed
failed
```

A failed initialization should be retryable from the first user message.

## Frontend fix

Inspect the New Chat handler in the CertEfficiency frontend.

It should resemble:

```ts
async function handleNewChat() {
  setNewChatError(null);

  try {
    const result = await createConv.mutateAsync();

    const conversation = result.conversation ?? result;

    if (!conversation?.id) {
      throw new Error("Conversation was created without an ID");
    }

    queryClient.setQueryData(["conversations"], (existing) => {
      // insert the newly created conversation safely
    });

    setActiveConversationId(conversation.id);
    navigate(`/conversations/${conversation.id}`);

    queryClient.invalidateQueries({ queryKey: ["conversations"] });
    queryClient.invalidateQueries({
      queryKey: ["conversation", conversation.id],
    });
  } catch (error) {
    console.error("new_chat_failed", error);
    setNewChatError("Couldn't start a new conversation. Please try again.");
  }
}
```

Verify the frontend reads the correct response shape. If the backend returns:

```json
{ "conversation": { "id": "..." } }
```

do not incorrectly expect:

```json
{ "id": "..." }
```

Normalize the response in one place.

## Button-state fixes

The New Chat button should be disabled only while the local create request is pending:

```ts
disabled={createConv.isPending}
```

It must not be disabled because:

* Sarah is generating an opening message
* another conversation has a failed Sarah job
* `activeJobId` from the previous conversation is set
* the warm runtime is starting
* a previous initialization failed

Clear any previous conversation-specific state before creating the new one:

```ts
setActiveJobId(null);
setSendError(null);
setNewChatError(null);
```

Do not reuse the prior conversation’s job state in the new conversation.

## Sarah initialization

```json
{
  "requestId": "<unique request ID>",
  "conversationId": "<local conversation ID>"
}
```

Normalize Sarah’s response:

```json
{
  "conversationId": "...",
  "message": {
    "type": "text",

  "actions": [],
```

Persist the opening message when it arrives, then invalidate:

```ts
["messages", conversationId]
```

Do not block local creation or navigation while waiting for Sarah.
